# A6.6 — Copy Audit (system-audio / capture honesty)

**Task:** BUILD-PLAN A6.6 (P0). **Rule (ADR 0002):** the UX must never imply
system-audio capture it does not actually perform, and must never imply
always-on capture. App Review reads this closely.

**Scope audited:** iOS `apps/ios/Wassup/**` + `apps/ios/BroadcastExtension/**`,
web `apps/web/src/**`, Android `apps/android/app/src/main/**`, all
`NS*UsageDescription` strings, notification/permission rationale copy, and
store-facing manifest metadata.

**Status:** READ-ONLY audit. No source was edited. Fixes are a later step.

---

## 1. What the capture paths ACTUALLY do (reality, from the code)

Read directly from the recorder/extension source so copy can be judged against
behaviour, not assumption.

| Path | File | Reality |
|---|---|---|
| **iOS mic recording** | `apps/ios/Wassup/Services/RecorderService.swift:146` (`start()`), `:161` `setCategory(.playAndRecord)`, `:172` AAC settings | `AVAudioRecorder` capturing the **device microphone only** (44.1 kHz mono AAC). No system/app audio. This is the only capture the shipped iOS UI can start. |
| **iOS broadcast (system audio + mic)** | `apps/ios/BroadcastExtension/SampleHandler.swift:142` `processSampleBuffer`, `:144` accepts `.audioApp` OR `.audioMic` | ReplayKit Broadcast Upload Extension. Captures **the foreground app's audio + the mic** into two AAC tracks — but ONLY while the user has started a broadcast via the OS ReplayKit picker. **Not wired to any in-app UI** (see finding N1). |
| **Android mic recording** | `apps/android/.../RecordingService.kt:103` `setAudioSource(MediaRecorder.AudioSource.MIC)` | Foreground service, `MediaRecorder`, **mic only**. Persistent notification while recording. |
| **Android broadcast (app audio + mic)** | `apps/android/.../BroadcastRecordingService.kt:471` `AudioPlaybackCaptureConfiguration`, `:489` `VOICE_RECOGNITION` mic | MediaProjection `AudioPlaybackCapture` (app playback) mixed with the mic. Only after the user grants the system MediaProjection consent dialog. Some apps opt out of playback capture → app audio may be silent, mic still recorded (`:362`, `:366`). |

**Web reality:** `Capacitor.getPlatform()` is hardcoded to `'web'` in the
shipped build (`apps/web/src/lib/native-shim/core.ts:6`). Therefore in the web
app **only mic recording exists** (browser `getUserMedia`). The entire broadcast
path in `App.tsx` is gated off on web: `startBroadcast` returns immediately with
an alert (`apps/web/src/App.tsx:355-358`). So on web, **no system-audio capture
happens at all.**

## 2. Violation table (copy that implies capture not performed / overstates)

| # | Sev | File:line | Current text | Why it's a problem | Recommended replacement |
|---|---|---|---|---|---|
| **V1** | **HIGH** | `apps/web/src/App.tsx:1993` | `{ type: 'online_meeting', title: 'Record Online Meeting', sub: 'Google Meet and Microsoft Teams', Icon: Bot }` — rendered unconditionally at `App.tsx:2103` (no platform filter) | In the shipped **web** build `platform` is always `'web'` (`native-shim/core.ts:6`), so tapping this card can NEVER capture anything — `startBroadcast` just alerts and returns (`App.tsx:355`). ## 3. Permission-string review (A10 rejection risk)

**iOS — `apps/ios/Wassup/Info.plist`:**

| Key | Line | Text | Verdict |
|---|---|---|---|
| `NSMicrophoneUsageDescription` | `:41` | "Wassup Doc records audio from this device so consultations and meetings can be transcribed and summarised for you." | **Review-ready.** Specific (what + why), honest, does not claim system audio. Optional tighten: add *when* — e.g. "…records audio from this device **while you are recording** so consultations and meetings can be transcribed and summarised." |
| `NSCameraUsageDescription` | `:43` | "Wassup Doc uses the camera to scan text from documents and images." | Good — specific and honest. |
| `NSPhotoLibraryUsageDescription` | `:45` | "Wassup Doc opens your photo library so you can choose an image to scan text from." | Good — specific and honest. |

No vague strings ("uses the microphone") that trigger recording-app rejections.
All three are purpose-scoped. Pass.

**Android — `apps/android/app/src/main/AndroidManifest.xml`:** Android has **no
usage-description strings**; runtime permission prompts (`RECORD_AUDIO` `:12`)
and the MediaProjection consent dialog are system-provided. The only app-authored
rationale surfaces are the notification channels, and they are honest:

- `RecordingService.kt:176-179` channel "Recording" / "Shows while Wassup is recording audio" + content text "Recording in progress…" (`:204`). Accurate (mic).
- `BroadcastRecordingService.kt:519-523` channel "Meeting recording" / "Shows while Wassup records an online meeting" + content text "Recording online meeting audio" (`:558`). Accurate — shown **only while the projection service is live**.

*A10/Play note (not a copy string):* the `mediaProjection` foreground type is
declared (`AndroidManifest.xml:41`), but Google Play requires a **prominent
in-app disclosure** before the MediaProjection consent for meeting capture. The
web `BroadcastInstructionSheet` provides it for the Capacitor build; the native
Compose client (Track B2) must carry the same disclosure.

## 4. Safe / accurate examples already in the code (use these as templates)

These are correct and should be the model for any capture copy:

- **System-audio disclosure (best template)** — shown immediately before the OS picker:
  - `apps/web/src/components/BroadcastInstructionSheet.tsx:70` (iOS): "iOS will let Wassup Doc **capture audio from your meeting app and your microphone**. Three steps:"
  - `:69` (Android): "Android will let Wassup Doc **capture supported meeting audio and your microphone**. Three steps:" — note "supported", honest about opt-out apps.
  - Step copy `:13-15` / `:19-21` ties capture to the explicit broadcast start ("Tap Start Broadcast…", "Approve Android screen/audio capture").
- **Mic-only disclosure (correct phrasing, does NOT claim system audio):**
  - `apps/web/src/components/InstantRecorderConsent.tsx:69`: "Wassup Doc **records audio from this device** for as long as you're recording…"
  - `apps/ios/Wassup/Features/Recorder/RecorderFlow.swift:28` and `:47`: same "records audio from this device" wording. Good.
- **Anti-always-on statement (perfect for App Review):**
  - `apps/web/src/pages/PrivacyPolicy.tsx:84-85`: "Recordings: audio files you record or upload. These are **only created when you tap a record button or choose a file** to import."
- **Honest capture-limit / consent copy:**
  - `apps/android/.../BroadcastRecordingService.kt:366`: "No meeting audio was detected. **Android may block playback capture for this app.**"
  - `apps/web/src/App.tsx:436`: warns Android may miss other speakers if the meeting app blocks internal audio capture — honest.
  - Consent checkboxes (`InstantRecorderConsent.tsx:84`, `BroadcastInstructionSheet.tsx:100`, `RecorderFlow.swift:55`) correctly place responsibility on the user for others' consent.

## 5. Notes / latent review risks (not copy violations, but flag for A6.6/App Review)

- **N1 (biggest App Review risk — iOS).** `apps/ios/BroadcastExtension/` ships in
  the bundle (a Broadcast Upload Extension that captures system audio + mic), but
  **nothing in `apps/ios/Wassup/**` starts it** — there is no
  `RPSystemBroadcastPickerView` anywhere, and Home only surfaces mic recording
  (`HomeView.swift:3` `CaptureAction` = recording/importFiles/scanText). A
  reviewer sees a system-audio-capture extension with no in-app trigger and a
  mic-only permission story. **Decide before submission:** either (a) surface the
  broadcast flow with the honest instruction copy from §4, or (b) exclude the
  extension from the iOS submission build until it is wired. Do not ship the
  extension unexplained.
- **N2 (iOS).** `NoteType.onlineMeeting` exists with a waveform label/icon
  (`Features/Files/FilesView.swift:34,334`; `Models/Note.swift:30`) but there is
  no way to create one on iOS. Harmless today; ensure any future entry-point copy
  matches §4 templates.
- **N3 (iOS).** `apps/ios/BroadcastExtension/Info.plist` has no
  `CFBundleDisplayName`, so the ReplayKit picker would show the raw target name.
  Set a human name ("Wassup Doc") if/when the broadcast flow is surfaced.

### Summary count
- **3 copy violations** (V1 HIGH, V2 low–med, V3 med) + **3 latent risks**
  (N1 high App-Review risk, N2/N3 minor).
- **Permission strings are review-ready** (iOS mic/camera/photos all
  purpose-scoped and honest; Android relies on system dialogs + honest
  notification rationale).
- The single most dangerous item is the pairing of **V1** (web advertises
  meeting/system capture it can't do) and **N1** (iOS ships a system-audio
  extension with no in-app trigger and mic-only copy). Both must be resolved
  before App Review / Play submission.

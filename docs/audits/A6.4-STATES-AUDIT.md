## 2. The four A6.4 P0 deliverables — gap analysis

### (a) Permissions explainer — mic + notifications

**Rule (BUILD-PLAN A7.3, `docs/BUILD-PLAN.md:416-417`):** never ask for push on first launch; ask
after the first recording.

| Item | Today | Verdict |
|---|---|---|
| iOS mic — purpose priming | Consent flow explains *recording behaviour & legal consent* (`RecorderFlow.swift:25-56`), but nothing primes the *OS mic prompt* that fires next inside `RecorderService.start()` (`RecorderService.swift:104,148`). | **partial** |
| iOS mic — denial recovery | `RecorderError.permissionDenied` text "…enable it in Settings." (`RecorderService.swift:118-119`) shown as an alert then screen dismisses (`RecordingView.swift:214`). **No deep-link to Settings, no in-context retry.** | **gap** |
| Web mic — purpose priming | `InstantRecorderConsent` explains recording; `getUserMedia` prompt fires at `App.tsx:1024`. Denial → `alert(...)` `:1027`. Unsupported browser → `:1019/:1076`. No Settings guidance, no retry affordance. | **partial** |
| iOS notifications — timing | `RecordingNotifier.requestAuthorizationIfNeeded()` is called from `AppEnvironment.startRecordingCapture()` **after** recording starts (`AppEnvironment.swift:108-111`), never on launch. **Correctly follows the rule.** | **present** |
| iOS notifications — explainer | The OS prompt is requested cold (`RecordingNotifier.swift:21-37`) with no soft pre-prompt explaining *why* ("we'll tell you when your notes are ready"). Also scope is `[.alert,.sound]` **local** only. | **partial** |
| Web notifications | No Notification API / permission request anywhere (only `messagingSenderId` in `firebase.ts:20`). | **missing** (belongs to A7.3 push — see §5) |

**Net:** the *recording* explainer exists on both platforms; a purpose-primed **mic** permission
explainer (with a Settings deep-link + retry on denial) and a soft **notification** pre-prompt do not.
Notification *timing* is already correct on iOS.

### (b) One-tap first recording

- iOS: hero capture card `HomeView.swift:240` → 2-step consent sheet → full-screen recorder.
- Web: primary action card `App.tsx:2103-2130` (`startAction('recording')`) → `InstantRecorderConsent` → recorder.

**Verdict: present, by design gated.** The primary record CTA is the most prominent element on both
home screens. It is not literally one tap — a consent checkbox is **required every session**
(`RecorderFlow.swift:52`, `InstantRecorderConsent.tsx:73-86`) for two-party-consent reasons, which is
intentional and should stay. Gap is minor: first-run users get no "tap here to make your first
recording" nudge pointing at the card.

### (c) Sample note

**Verdict: missing — both platforms.** No seed, no sample, no placeholder note anywhere (confirmed by
repo-wide search; the only "first run" reference is a comment at `RecordingNotifier.swift:16`). This is
the single largest A6.4 deliverable gap: a first-run user on either surface lands on an app with zero
content and no worked example of what a finished note looks like. Web Home doesn't even render an empty
state (§1), so the void is most visible there.

### (d) Per-pipeline-stage user-visible failure state (recorded → uploading → processing → ready → failed)

| Stage | User-visible failure + plain-English cause | Retry | Anchors |
|---|---|---|---|
| recorded (capture) | **present** — salvage + named cause (mic taken, route lost, disk full, cap) | keep-and-save partial | iOS `RecorderService.swift:60-74`, `RecordingView.swift:172-191`; web `App.tsx:1050-1063` |
| uploading | **present** — `UploadError` messages, note marked error, resume-on-network | retry (re-upload from disk) | iOS `UploadService.swift:10-25`, `AppEnvironment.swift:245-252,284-298`; web `App.tsx:1295-1368` |
| processing (transcode/STT/summary) | **partial** — one generic "Processing failed" pane; **cause is only as good as backend `errorMessage`**, fallback is generic; stages not distinguished to the user | **present** — Try again | iOS `NoteErrorPane.swift:13-22`, `NoteDetailView.swift:182`; web `App.tsx:1840-1857` |
| stuck / timeout | **present** — watchdog flips to error "Processing took too long. Please try again." | Try again | web `App.tsx:602-635`; iOS `StuckBudgets.swift` + `NotesRepository.resetStuckGuard` |
| ready | **present** — full note render | n/a | iOS `NoteDetailView.swift:179`; web `:1859+` |
| **partial success** (transcript OK, summary failed) | **missing** — a single `status==error` shows the error pane and **hides the transcript**; no "summary failed but transcript readable + regenerable" state | — | iOS `NoteDetailView.swift:178-191`; web `App.tsx:1830-1858` (overlaps **A7.4** — see §5) |

**Net:** the linear pipeline is well covered end-to-end with retry. Two gaps: (1) the processing
failure pane is generic rather than stage-specific with a plain-English cause; (2) there is no
partial-success state (A7.4 requirement — cross-referenced, not re-scoped).

## 4. Prioritised punch list (states to build)

### P0 — iOS
- Build a **sample/welcome note** seeded on first sign-in so the user sees a finished summary+transcript before recording. *(A6.4-c)*
- Add a **mic-permission explainer** step (priming copy before the OS prompt) and, on denial, a pane with a **"Open Settings" deep-link** + retry — replace the dead-end alert at `RecorderService.swift:118`/`RecordingView.swift:214`. *(A6.4-a)*
- Add a **soft notification pre-prompt** before `RecordingNotifier.requestAuthorizationIfNeeded()` (`AppEnvironment.swift:111`) explaining "we'll tell you when your notes are ready" — keep the after-first-recording timing.
- **Surface `listenerHealthy`** (`NotesRepository.swift:74`) in Files/Home as a "can't load your notes — pull to refresh" banner; today the failure is silent. *(error #15)*
- Split the processing-failure pane (`NoteErrorPane`) to name the **stage** that failed with a plain-English cause. *(A6.4-d)*

### P0 — web
- Add a **Home first-run / empty state** (`App.tsx:2006-2186`) — currently Home renders no empty block; point new users at the record card. *(A6.4-b nudge)*
- Build the **sample/welcome note** (parity with iOS). *(A6.4-c)*
- Add a **mic-permission explainer + denial-recovery** (Settings/site-permissions guidance + retry) replacing the bare `alert()` at `App.tsx:1027`. *(A6.4-a)*
- Move **sign-in errors** from `alert()` (`App.tsx:1565,1576`) to an inline message on the login card.
- Stage-specific processing-failure cause in the note-detail error block (`App.tsx:1840-1857`). *(A6.4-d)*

### P1 — shared
- Add explicit **Retry** buttons to chat (`ChatView.swift:243` / `ChatTab.tsx:137`) and search (`FilesView.swift:366` / `SearchTab.tsx:132`) errors — today recovery is re-type/re-submit only.
- First-run **coach nudge** pointing at the primary record card on both Home screens.
- Add an **"offline" affordance** at record time (banner) so the local-first behaviour is legible (coordinate with A7.1).
- Login **onboarding value-prop** beyond the one-line tagline (`LoginView.swift:23` / `App.tsx:1552`).
